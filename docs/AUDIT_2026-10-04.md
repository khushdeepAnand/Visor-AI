# StockPilot reliability, engineering, and trading audit

Audit date: 2026-10-04. Environment: Windows, Python 3.12.10, Node 24.18.0, npm 11.16.0.

## Executive assessment

The supplied v16 ZIP was not a distinct application upgrade: every application file it contained matched the corresponding file in `StockPilot-AI-v6.1-SECURE` byte-for-byte before repairs. It omitted files needed for a clean installation. The application internally identifies itself as 7.0.0-rc.1. Folder names v6 and v16 therefore do not establish different application versions.

The most important reproducible failure was packaging: `npm run build` executes a prebuild command referencing an absent generator. The installed source tree also relied on undeclared packages already present in node_modules, hiding clean-install failures. The Windows secret store lacked the two keys required by the launcher.

The confirmed failures described below were repaired. Startup and browser workflows were checked. This establishes a repaired local application, not a guarantee against every future crash or proof of profitable trading. External providers, network outages, Windows permissions, disk exhaustion, and new data regimes still require operational monitoring.

## Confirmed findings and repairs

### 1. Release omitted the API client generator — startup blocker

- Evidence: `npm run check:api` from the extracted original ZIP failed with `MODULE_NOT_FOUND` for `frontend/scripts/generate-api-client.mjs`.
- Mechanism: package.json prebuild invokes that file. The release allowlist omitted frontend/scripts.
- Repair: include frontend/scripts in the release payload; retain a working generator and check that generated routes match the committed OpenAPI schema.
- The current generated contract contains 166 routes and 58 schemas.

### 2. Release omitted Alembic assets — incomplete optional database deployment

- The original ZIP omitted alembic.ini and the alembic directory although scripts/run_migrations.py refers to them.
- Repair: include migration assets in the release allowlist. Add required-runtime checks and make the release builder reject incomplete inputs.
- These files being present does not establish successful PostgreSQL or SQLCipher deployment. See remaining work below.

### 3. Windows secret-store initialization was incomplete — startup blocker

- Evidence: `manage_secrets.py status --require STOCKPILOT_JWT_SECRET STOCKPILOT_MFA_SECRET` reported both keys missing.
- Repair: run the existing bootstrap command. It initialized the current-user Windows DPAPI store and cleared plaintext secret assignments from the local environment file.
- Python setup/start entry points now delegate to the existing PowerShell implementation on Windows. This gives both entry points the same secret handling and process-tree cleanup.
- Secret values are not included in this report or the repaired ZIP. DPAPI data is user-specific and is not portable to another Windows account.

### 4. Production build missing was not detected by normal launch

- Existing first-run detection checked node_modules, Python and .env but did not check frontend/.next/BUILD_ID.
- Repair: first-run detection now recognizes missing production output; direct start gives a clear setup instruction before launching processes.

### 5. Undeclared Storybook dependency broke a clean production build

- Evidence after reinstalling declared dependencies: TypeScript could not resolve @storybook/react-vite in the story files.
- Mechanism: production type checking included optional Storybook authoring files even though package.json does not declare Storybook.
- Repair: exclude .storybook and *.stories.tsx from the application's production tsconfig. Runtime application files remain strictly checked.
- Storybook is still an optional, separately unverified tool; its stories are not deleted.

### 6. Undeclared accessibility-test dependency broke verification

- Evidence after reinstalling declared dependencies: Vitest could not resolve jest-axe.
- Repair: declare and lock jest-axe 11.0.0 and @types/jest-axe 3.5.9 as development dependencies. Add typed test matcher declarations for Vitest and jest-dom. The existing accessibility tests and clean TypeScript build then run again.

### 7. Critical Next.js advisory

- npm audit identified Next.js 16.3.3 in the affected range for GHSA-vcvr-r3jv-pc5j, a next/og ImageResponse remote-code-execution advisory.
- Repair: pin Next.js 16.3.8 and regenerate package-lock.json using npm.
- Verification: production build passes; npm audit --omit=dev --audit-level=high reports zero vulnerabilities at the time of this audit.
- This is a dependency-audit result, not a whole-application penetration-test result.

### 8. Readiness falsely returned success when the database was unavailable

- Mechanism: /api/v1/ready always returned HTTP 200, even with status=not_ready. Both launchers treated any 2xx response as ready.
- Repair: return HTTP 503 when the database health check is not Operational. A regression test verifies refusal.
- Application readiness remains distinct from market-feed readiness: the terminal can start while a provider is unavailable.

### 9. Browser storage failures could break the shared market provider

- Mechanism: an unguarded localStorage.setItem effect in MarketContext could throw when device storage was blocked or full.
- Repair: keep the in-memory workspace usable when saving that preference fails.
- Other persisted-layout and device-storage paths warrant further hardening; this was not a browser-storage-wide rewrite.

### 10. Margin presentation contradicted available data

- An available standalone margin estimate also rendered an "unavailable / Unknown reason" block because its state did not use the PayoffMargin shape.
- Strategy Lab lost margin_unavailable_reason when margin was null.
- Repair: remove the contradictory block, show the backend reason for missing estimates, retain scenario details, and label the estimate as non-official.
- Volatility-change signs now render correctly for negative scenarios.
- Approximate SPAN-style values remain estimates, not broker or exchange requirements.

### 11. Evaluation arithmetic defects

- Ensemble CRPS incorrectly scored the mean forecast rather than averaging member absolute errors. Its 3D fill_diagonal call could fail for ordinary non-cubic ensemble shapes. Single-member subtraction could broadcast across observations.
- Repair: implement the empirical ensemble CRPS formula with observation/member shape validation. Known-distribution and single-member regressions verify expected results.
- Baseline comparison used differences between baseline predictions instead of aligned baseline forecast errors. This could misstate relative skill.
- Repair: when a matched baseline is supplied, use the model MAE divided by that baseline's aligned MAE. The result occupies the existing mase field for compatibility; it is an aligned relative-MAE measure, not a training-scaled textbook MASE.
- A one-row series produced an empty-mean/NaN scale estimate. It now refuses to claim measured skill by returning infinity.
- Directional scoring used np.roll, making the first observation reference the last observation. Remove this wraparound and exclude the initial observation lacking an earlier reference.
- Multi-symbol evaluation still needs explicit per-symbol, per-horizon timestamp alignment. Approximate PIT and reconstructed quantile diagnostics should not be treated as audited probabilistic evidence.

### 12. Verification defects masked real regression status

- Two cross-user paper-order tests relied on external market data and returned 503 before reaching their ownership assertions. They now inject an explicit synthetic quote only within those tests. Production data policy is unchanged.
- Two promotion tests incorrectly expected every passed receipt to assign a symbol to the canary. They now distinguish a valid control arm and explicitly select 100% rollout for the forecast-wiring test.
- MarketContext tests selected an unrelated provider-health status banner. They now identify the demo banner specifically.
- Six browser authentication/session tests used obsolete API payloads, nonexistent setup/revoke routes, and ambiguous password selectors. They now exercise current login, onboarding, account MFA, session deletion, and all-session logout contracts.
- No security or publication gate was loosened to obtain passing tests.

### 13. The installation lock omitted declared telemetry and passkey packages

- A new virtual environment could start the application, but three tracing tests failed and passkey tests skipped because the optional libraries were absent.
- Repair: add the exact working OpenTelemetry 1.45.0 / instrumentation 0.66b0 dependencies and WebAuthn 2.8.0 dependencies to requirements-dev.lock. Tracing remains disabled unless configured; passkey availability now matches the installed library.
- Verify that enabled integrations have matching runtime dependencies rather than relying on packages left in an old virtual environment.

### 14. Tests depended on the user's environment-file provider mode

- Fresh setup uses the example environment file. Its offline mode caused authentication tests to violate their intended local-only test JWT policy.
- Repair: explicitly select LIVE_ONLY in tests/conftest.py before imports, alongside STOCKPILOT_ENV=test. Individual provider tests still override mode as needed. This isolates test configuration; it does not weaken runtime authentication.

### 15. Background jobs contained broken service calls

- Root scheduler.py used trace_market_data_operation without importing it. Refresh jobs caught the resulting NameError and never completed their intended work. Add the missing import.
- The settlement replay task called a keyword-only settlement function with positional arguments. Its user-scoped intent was also unsupported by the underlying selector.
- Repair: use keyword arguments and add optional user_id filtering at the pending-ledger SQL query, before LIMIT. Normal global maintenance retains its existing behavior. A two-user regression verifies scoped selection.
- The retention task imported nonexistent run_retention_sweep. Call the existing run_retention_enforcement service. Regression checks exercise both task contracts.

## Existing strengths worth retaining

1. Explicit India-only catalogue validation and source provenance.
2. Separate LIVE_ONLY, FALLBACK_ALLOWED and OFFLINE_DEMO modes.
3. Per-user ownership checks and isolated test databases.
4. Forecast guardrails, promotion gate, canary routing, immutable outcome settlement and drift components.
5. Shared quote fan-out with streaming-to-REST fallback and bounded caches/jobs.
6. Paper-only order simulation, rather than silently executing broker orders.
7. Same-origin authenticated REST proxy and shared browser session state.

## Remaining engineering risks and suggested changes

### Priority 0: dependable daily use

- Verify market-feed health during a real Indian trading session. Test expired/revoked tokens, reconnects, rate limits, delayed ticks, market close, holidays and a provider outage.
- Publish exchange as-of time, receipt time, provider, delay, source mode and corporate-action adjustment basis next to every price. Preserve stale labels after disconnect.
- Make a no-trade/unavailable decision explicit when data quality, liquidity or forecast evidence is insufficient. A neutral blank state is better than fabricated conviction.
- Test release installation in a new Windows account with no preexisting virtual environment or node_modules. Test paths containing spaces, offline retry, interrupted setup, disk permission denial and port conflicts.
- Keep the active SQLite database out of a cloud-sync workflow where feasible. Use the SQLite backup API and verify restoration. Do not manually merge root stockpilot.db with database/stockpilot.db; determine ownership and migrate deliberately.
- Optional PostgreSQL DAO/Alembic paths are not the normal API persistence path. scripts/run_migrations.py currently suppresses migration failures and its environment selects URLs differently from the caller. Implement an explicit, verified migration workflow before claiming production PostgreSQL support.
- Standardize one application version across manifests, startup output, release name and documentation.

### Priority 1: credible quantitative evidence

- Evaluate true per-symbol/per-horizon out-of-sample returns with point-in-time universes, delisted securities, survivorship controls and corporate-action adjustments.
- Compare against persistence, historical-volatility corridors and simple trend baselines. Report calibration, interval width, drawdown and net trading results, not only R-squared or directional hit rate.
- Apply walk-forward splits, purge/embargo for overlapping horizons, fixed holdout periods and multiple-testing controls for strategy selection.
- Use actual predicted quantiles or a justified predictive distribution for pinball/CRPS/PIT diagnostics. Separate reconstructed approximations from promotion evidence. Recheck historical receipts after changing metric definitions.
- Publish an immutable forward scorecard with sample counts, timestamps, confidence bounds, unscorable outcomes and model/data versions. Never mix synthetic outcomes with live evidence.
- Reject or downgrade unconverged fits and log the selected fallback model. Test whether existing publication gates actually refuse unreliable models rather than merely displaying warnings.
- Make scheduled settlement/drift jobs observable and enabled intentionally. A component existing in code is not evidence that the live scorecard is being updated.

### Priority 2: improve trader utility

- Build a focused pre-market and live-session workflow: watchlist, event calendar, key levels, volatility regime, liquidity filter and risk plan on one screen.
- Add expected transaction costs for India: brokerage, STT, exchange charges, GST, SEBI charges, stamp duty, spread and slippage. Separate intraday/delivery and instrument cases; version tariff assumptions.
- Add position sizing by maximum rupee risk, portfolio concentration, correlated exposures, gap risk and daily loss limits.
- Extend paper fills with observed bid/ask, order-size participation, partial fills, liquidity and latency. Never imply a paper fill is achievable live.
- Resolve derivative contracts using instrument master, current lot sizes and exchange expiry rules. Use broker risk files for official margin if available; keep estimates visibly separate.
- Add an exportable trading journal connecting the original thesis, data snapshot, risk plan, entry/exit and post-trade outcome.
- User-test calm mode and mobile layouts with active traders. Prioritize quick symbol switching, saved layouts, reconnect feedback and accessible controls over additional model names.

### Priority 3: deployment readiness

- Measure concurrent users, WebSocket subscriptions, forecast queue latency, memory growth and database-lock contention before scaling.
- Process-local caches, quota state and thread pools are local-runtime capabilities. Use shared stores or durable workers only when measured multi-instance needs justify them.
- Verify enabled optional packages against the installation lock. Passkeys and telemetry are now included. SQLCipher, PostgreSQL and Celery remain separate optional deployment concerns.
- Finish the unsilenced Python typing gate before treating the full release verification pipeline as green.
- Keep read-only market-data integration distinct from any future execution integration. If personalized investment advice or public commercial distribution is planned, obtain an applicable Indian regulatory and market-data licensing review.

## Run the repaired application

Existing installed project:

1. Open `StockPilot-AI-v6.1-SECURE`.
2. Double-click `START_STOCKPILOT.bat`.
3. Keep its console open; use http://127.0.0.1:3000.
4. Stop with Ctrl+C. If ports 8000/3000 are occupied, follow the launcher's PID instructions.

Fresh installation:

1. Extract `StockPilot-AI-v16-WINDOWS-REPAIRED.zip` into a writable folder.
2. Run `RUN_STOCKPILOT.bat`; first-run setup installs declared dependencies and builds the frontend.
3. Configure the intended provider mode and read-only data credentials through the existing setup tools.
4. Synthetic demo is useful for learning and smoke tests. It is not evidence for a live trading decision.
